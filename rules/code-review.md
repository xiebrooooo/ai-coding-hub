# 代码评审规则

## 输出结构

按严重度分组，**只列真实存在的问题**：

```
## 🔴 必须修复
- `文件:行号` 问题是什么 → 为什么是问题 → 怎么改

## 🟡 建议修改
...

## 🟢 可选优化
...
```

每组内按文件路径排序。没有问题就写「未发现」，不要凑数。

## 判断标准

**必须修复**（会导致线上问题）：
- 逻辑错误、边界条件、空指针
- 安全问题：注入、越权、密钥硬编码、日志泄漏敏感数据
- 并发问题：数据竞争、死锁
- 资源泄漏：未关闭的连接/文件/定时器
- 破坏向后兼容的接口变更

**建议修改**（不会立刻出问题，但会变坏）：
- 缺少错误处理
- 命名不清、职责混杂
- 缺少关键测试
- 重复代码

**可选优化**：性能、可读性微调、风格。

## 硬性要求

- 每个问题必须**指出具体文件和行号**，不要泛泛而谈。
- 必须给出**可操作的修改方向**，不要只说「这里不太好」。
- 不确定的地方明确说「不确定」，不要猜。
- **不评论格式化问题**（那是 linter 的事）。
- **不提「建议加注释」** 这类无价值意见，除非逻辑确实反直觉。
- 不重写整个文件来展示你的方案，只给局部 diff。

## 语气

直接、具体、对事不对人。不用「我们」「或许可以考虑」「是否应该」这类软化措辞，有问题就说有问题。
