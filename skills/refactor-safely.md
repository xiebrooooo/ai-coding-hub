# 安全重构

**触发**：用户要求重构、整理、拆分类 / 函数，或者要改一段「没有测试但很重要」的代码。

**第一原则**：重构 = **行为不变**地改结构。
如果你同时改了行为，那叫「重写」，必须分开做、分开提交、分开测试。

## 步骤

### 1. 明确边界
动手前先写下：
- 要重构哪些文件/函数
- **明确不动**哪些部分
- 这次重构的**验收标准**是什么（例如「外部接口签名不变，所有现有测试通过」）

产出给用户确认，再动手。

### 2. 建安全网
- 如果有测试：先跑一遍，确认**当前是绿的**。测试是红的就别重构，先修。
- 如果没测试：先补 characterization test —— 不判断行为对不对，只**记录当前实际行为**（包括那些看起来像 bug 的行为）。用真实输入跑一遍，把输出固化下来。

这一步不能跳。没有安全网的重构是在赌。

### 3. 小步改，每步验证
每一小步都要：
- 只做一种变换（提函数 / 换名字 / 移文件 / 换数据结构），不混合
- 改完立刻跑测试
- 通过就提交一个 `refactor:` 提交（**不要在重构提交里夹带功能改动**）

### 4. 卡住了就退
- 如果跑了 3 步还是红的，`git reset --hard` 回到上一个绿点，重新想。
- 不要在红的树上继续叠加修改来「修好它」—— 你会同时失去对两边的判断。

### 5. 收尾
- 跑完整测试套件 + 类型检查 + lint
- 对比重构前后的公开 API（类型签名、导出符号），确认没有意外变更
- 输出一份改动摘要：动了什么、为什么、怎么验证

## 禁止

- ❌ 重构 + 修 bug + 加功能 混在一个提交里
- ❌ 没有测试就直接大改
- ❌ 「顺便优化一下」—— 顺手改的东西永远没人 review
- ❌ 一次重命名跨越 200 个文件且无法 review
