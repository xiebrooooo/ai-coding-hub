# 给遗留代码补测试

**触发**：需要修改一段没有测试的代码，或者用户说「这块没人敢动」。

## 核心思路

不要试图搞清楚「这段代码应该做什么」——那是重构阶段的事。
现阶段只回答「**它现在实际做了什么**」，把它钉住。

## 步骤

### 1. 找接缝（seam）
先找可以插桩的边界，优先级从高到低：

1. 纯函数（最容易测）
2. 类的公开方法（依赖用构造注入）
3. 模块导出函数（用依赖替换 / mock）
4. 全局状态、单例、静态调用（最难，通常要先用 `Extract and Override` 把依赖提出来）

### 2. 写特征测试
- 输入用**真实的生产数据样例**（脱敏后），不要自己编。
- 断言**当前实际输出**，即使它看起来是错的。如果发现疑似 bug，用 `// 疑似 bug：...` 注释标出来，但测试仍按现状写。
- 每个测试只覆盖一条路径。分支多就多写几个。

### 3. 确认测试有意义
对每个新测试做**变异验证**：手动改一处业务逻辑，确认至少有一个测试变红。
全绿说明测试没测到东西。

### 4. 固定外部依赖
- 时间：注入 clock，或 mock `Date.now`
- 随机：固定 seed
- 网络/DB：替换成假实现，**不要在单测里连真实服务**
- 文件系统：用临时目录，测完清理

### 5. 报告
输出：覆盖了哪些路径、还有哪些没覆盖（明确列出来）、发现的疑似 bug 清单。

## 禁止

- ❌ 为了让老代码「可测」而大规模改动它（那是重构，单独做）
- ❌ 断言写得含糊（`expect(result).toBeTruthy()` 这种等于没测）
- ❌ 一个测试塞进十个场景，失败时定位不了
- ❌ 依赖执行顺序的测试（`beforeAll` 里塞共享状态）
