# 系统化排查 Bug

**触发**：用户报告了一个 bug，或者测试挂了。

**铁律**：在拿到「能稳定复现的最小用例」之前，不准修改任何代码。
改代码的冲动是调试最大的敌人。

## 步骤

### 1. 复现
- 写出**最小的复现步骤**：什么输入、什么操作、期望什么、实际什么。
- 复现不了就问用户要：完整报错、环境版本、最近改动。
- 复现不了还硬改 = 制造新 bug。

**产出**：一段可以贴进 issue 的复现描述。

### 2. 定位
按成本从低到高，逐层缩小范围：

1. **读报错**：完整堆栈，第一个属于本项目的栈帧是关键。
2. **看 diff**：`git log -p -n 20 -- <相关路径>`，多数 bug 来自最近的改动。
3. **二分**：`git bisect` 定位是哪个提交引入的。
4. **加日志**：在关键路径打印输入输出，确认「以为是什么」和「实际是什么」的差异。
5. **断点/单步**：日志不够时用调试器。

**产出**：一句话的根因假设，例如「空字符串没被校验，导致下游 parseInt 返回 NaN」。

### 3. 验证假设
**先证明假设成立，再动手改。** 方法：临时改一行让假设"必然失败"，看现象是否随之改变。

如果改了但现象没变 → 假设错了，回到第 2 步。不要在这个假设上继续叠加修补。

**产出**：确认的根因。

### 4. 修复
- 只改根因，不要顺手重构、不要顺手格式化。
- 修复方案要能解释**为什么这样改就不会再出现**。

### 5. 防回归
- 加一个测试，**在修复前必须是失败的**，修复后通过。验证方法：临时回滚修复，确认测试确实会红。
- 如果这是个能被同类代码重复犯的错，在对应位置加注释或类型约束。

## 禁止

- ❌ 猜着改，改完看「好像好了」
- ❌ 加 `try/catch` 把错误吞掉让它「不报错」
- ❌ 用 `setTimeout` 或重试掩盖竞态
- ❌ 同时改多个地方，导致不知道哪个生效了
- ❌ 报「已修复」但没试过原复现步骤
