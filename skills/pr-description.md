# 生成 PR 描述

**触发**：用户说「写一下 PR 描述」「这个分支要提 PR」。

## 步骤

1. 获取 diff 范围（默认相对主分支）：
   ```bash
   git log --oneline origin/main..HEAD
   git diff origin/main...HEAD --stat
   ```
2. 读完整 diff，**逐个文件**判断改动意图。不要只看文件名猜。
3. 如果 diff 里有看不懂的改动，先在描述里标出来问我，不要编造理由。
4. 按下面的模板输出。

## 模板

```markdown
## 做了什么

<!-- 2-4 条，动词开头。每条说清「什么变了」，不要写「优化了代码」这种空话 -->
- 新增 X 接口，支持 Y
- 修复 Z 场景下 N 为空的崩溃

## 为什么

<!-- 关联 issue / 用户反馈 / 技术债。没有明确的理由就写「技术债偿还：X 已不可维护」 -->

Closes #123

## 怎么测

<!-- 给 reviewer 可直接执行的步骤，不要写「跑一下测试」 -->
1. `pnpm dev` 启动
2. 访问 `/settings`，把语言切成英文
3. 预期：页面不刷新，文案立即变化

## 风险与影响

<!-- 影响面、破坏性变更、回滚方式。没有就写「无」 -->
- 接口 `GET /api/v1/users` 的响应新增字段 `avatar_url`（向后兼容）
- 回滚：`git revert` 即可，无数据迁移

## 自查

- [ ] 本地跑通 `<测试命令>`
- [ ] 无新增 lint / type 错误
- [ ] 无调试代码残留（console.log / print / debugger）
- [ ] 涉及 UI 的已附截图
```

## 质量要求

- 「做了什么」和「为什么」必须分开，很多 PR 只写了前者。
- 测试步骤要具体到能照着点。写「验证功能正常」等于没写。
- 改动超过 400 行时，主动建议拆分。
- 有破坏性变更时，**放在最顶部用醒目提示**，不要藏在末尾。
